# AGENTS.md — Project 5: Search-Based Test Generation

## Mission

Build the complete, reproducible `search-based-test-generation` Python research project. This is the fifth and final repository in the approved five-project portfolio. The research question is: **Can a genetic algorithm generate integer-valued tests achieving higher branch coverage than random testing under equal objective-evaluation budgets?** Distinct challenge: search-based software engineering (SBSE), not another feature-selection study.

Read `docs/PROJECT_SPEC.md` in full before coding. It is the scientific contract. Prefer simple, typed, testable modules; no unrelated framework, dynamic source rewriting, remote targets, or elaborate multi-objective optimizers. Code, commits, documentation, PRs and result artifacts are in professional English. Complete implementation and verify it; the user will study the code separately.

## Experimental validity

1. Create exactly **six small, deterministic, pure Python functions** with hand-inspectable, atomic conditional branches, using the fixtures and branch definitions in `docs/PROJECT_SPEC.md`. Five have two integer inputs; one has three. All inputs lie in `[-20, 20]` inclusive. Inventory exactly **18 conditional decisions / 36 decision outcomes** (true and false), each feasible inside the domain. Distinguish these predeclared fixture branch outcomes from all Python interpreter/control-flow arcs.
2. Every candidate is a **single test input** for the function being targeted. The real target function executes exactly once per optimizer objective evaluation; the actual outcomes observed during execution are logged. Do not award branch coverage based on unevaluated predicates, guessed outcomes, simulated/sidecar coverage, or evaluations outside the budget. Preserve the complete candidate archive (including duplicates) and measured cumulative coverage after each evaluation.
3. Define correct integer **branch distance** for both truth directions of `<`, `<=`, `>`, `>=`, `==`, `!=`; implement testable control-dependence/approach-level handling for nested targets. Optimize one predeclared target outcome at a time with `fitness = approach_level + distance/(1+distance)` for misses, `0` when target observed. Normalize only the branch-distance term. Do not let target guidance inadvertently count unexecuted branches as covered. No hidden target-solution oracle is permitted during optimization.
4. Both GA and Random Search use **identical** decoded domains, deterministic target order, 60 evaluations per target, population 12 and paired independent seeds `0..19`. Each method must consume exactly `36*60=2160` fixture calls per run; total expected `86,400` fixture calls across 20 seeds and 2 methods, barring explicitly documented legitimate failures. Evaluation budget counts actual test-function invocations; do not count only unique candidates or full generations. Preserve duplicates and measure them. If any extra oracle, reachability, minimization or verification executions occur, log them *separately* and exclude them from the search budget explicitly.
5. Random Search must sample independently without guidance. GA uses the continuous reference operators with documented clipping/mutation and integer decoding; this discretization is an important limitation. Never assume GA will win. Report equal budgets, identical target schedule, coverage trajectories, final coverage, time, discovered branches, uniqueness, seed variation and generated suite sizes. Quantify negative/tied results honestly; do not make unsupported statistical significance claims.
6. Validate all branch outcomes are feasible by a separate **offline exhaustive reference audit** on the bounded domain; keep any found witness inputs out of search initialization and fitness. Add independent hand-written reference tests for function outputs and branch traces, not solely generated regression tests derived from the same implementation. Generated suite assertions are regression snapshots, not independent correctness oracles.
7. Use a deterministic greedy set-cover pass to select a smaller suite from **evaluated** archived candidates, with documented tie-breaking and no new search evaluations. The suite must retain the same observed branch coverage as the complete archive; verify by replay and disclose those replay calls outside the search budget. Report suite size separately from objective calls.
8. Record preregistered/protocol configuration and source/dependency hashes in a study manifest before the full run, then genuine raw per-seed results, per-evaluation trajectories, summaries, plots and audit evidence. The benchmark is a white-box study with known target code and has **no untouched ML holdout**. Do not manufacture a holdout or claim cross-program generalization. Do not use exhaustive reachability witnesses to seed either optimizer.

Do not rerun all 86,400 evaluations on every CI push. Gate artifact-dependent CI on study phase, so a committed pre-run protocol does not cause spurious failed checks.
